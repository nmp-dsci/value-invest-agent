Can an agent learn to make the calls a value investor makes on YouTube?

Four years of Value Investing with Sven Carlin, Ph.D. (@Value-Investing) turned into a golden set of dated stock calls; an analyst agent that sees only the prices and financial statements available on the video date and tries to reproduce each call; and a validator that scores both the channel and the agent against what the stock actually did 6, 12 and 24 months later.

2,072 video ids listed by Supadata (channel reports 2,400) ≈1,000 published in the 4-year window 270k subscribers 9 / 40 recent titles contain an explicit ticker transcript·lab reused for ingestion + chunks
00

The idea, in one figure

Every stock-analysis video is a labelled example: a date, a ticker, and a stance (buy / hold / sell / watch) plus the reasoning behind it. Two things can be learned from that at once — whether an agent can reproduce the human's call from the same public data, and whether the human's calls were any good.

Point-in-time rule. The agent must never see anything dated after the video. Prices are cut at T0; financial statements are filtered on filing/report date ≤ T0, not fiscal period end. This is the invariant that makes the comparison honest and it is enforced in one place (§4).

02

Architecture: two repos, one corpus

transcript·lab (transcript-rag-agent) already does everything transcript-shaped: Supadata discovery with a disk cache, transcript fetch + normalisation, segment-aware chunking, MiniLM embeddings, a Chroma store with raw_transcripts / transcript_chunks collections, a bulk-index channel --since --until CLI, and an API (/api/corpus, /api/corpus/{video_id}/chunks, /api/index/queue). Every chunk already carries channel_id, title, upload_date, so channel-scoped retrieval is native. value-invest-agent owns everything that is finance-shaped and points at transcript·lab's corpus by video_id and chunk:<video_id>:<index>.

reuse transcript·lab

Discovery + cache, Supadata fetcher with polling and retries, chunking, embeddings, Chroma stores, bulk-index CLI, corpus API, RAG retrieval for "what did he say about X before?" few-shot context.

  • src/transcripts/discovery.py
  • src/rag/storage.py RawTranscriptStore / TranscriptChunkStore
  • src/cli.py bulk-index channel

reuse ConvFinQA-agent patterns

The single LLM chokepoint (llm.py: demo gate, retry/timeout, no model at import), Pydantic AI per-stage agents with structured outputs, MLflow tracking + a champion/challenger gate, a keyless demo mode.

reuse DABStep / tau2 loop

The scored, self-improving prompt loop: a teacher diagnoses first-wrong cases and proposes one prompt version; a gate promotes only on a significant, net-positive delta. Same shape for "make the agent match the golden calls".

new finance layer

Title classifier + ticker resolution, golden extraction schema, yfinance/EDGAR loaders, the as_of point-in-time view, forward-return validator, DuckDB schema, and the walkthrough app.

03

Storage: where does each thing live?

The question raised: can this project use transcript·lab's database with its own schema? transcript·lab's "database" is Chroma — a vector store with per-document metadata, no relational schema, no joins, no dates as dates. It is the right home for transcripts and chunks and the wrong home for prices, statements and scored predictions. So the answer is yes for transcripts, no for the rest:

A · Everything in Chroma

Store calls/prices as metadata on chunk-like documents.

no joins no time-series one repo owns all state

Forward-return maths and as-of filtering become Python loops over metadata dicts. Rejected.

B · Chroma for text, DuckDB for facts recommended

Transcripts + chunks stay in transcript·lab's Chroma (channel-scoped). Structured data lives in data/value_invest.duckdb, schema vi, in this repo. Foreign keys are transcript·lab's own ids.

SQL joins + window fns one file, no server pandas/parquet native two stores to keep consistent

Consistency is one-directional and cheap: vi.videos is rebuilt from transcript·lab's corpus API; nothing in Chroma depends on DuckDB.

C · Shared Postgres, schema vi

A Postgres schema both repos could read; transcript·lab would gain a relational catalog.

true shared schema new service to run + deploy touches transcript·lab

Right answer if a third project needs the same tables. Not yet.

The vi schema

-- data/schema.sql (excerpt) — applied by `uv run vi db init`
CREATE SCHEMA IF NOT EXISTS vi;
CREATE TABLE vi.videos (
  video_id TEXT PRIMARY KEY, title TEXT NOT NULL, published_at DATE NOT NULL,
  duration_s INTEGER, kind TEXT CHECK (kind IN ('single','multi','macro','other')),
  classifier_version TEXT, reviewed_by TEXT, transcript_status TEXT DEFAULT 'none');
CREATE TABLE vi.calls (
  call_id TEXT PRIMARY KEY, video_id TEXT REFERENCES vi.videos, ticker TEXT NOT NULL,
  exchange TEXT, t0 DATE NOT NULL, stance TEXT CHECK (stance IN ('buy','hold','sell','watch','avoid')),
  intrinsic_value DOUBLE, price_at_t0 DOUBLE, horizon_years DOUBLE,
  thesis JSON, risks JSON, evidence_chunk_ids JSON, extractor_version TEXT,
  curation_status TEXT DEFAULT 'auto');            -- auto | reviewed | rejected
CREATE TABLE vi.statements (
  ticker TEXT, period_end DATE, filed_at DATE, kind TEXT, freq TEXT,
  line_item TEXT, value DOUBLE, source TEXT, PRIMARY KEY (ticker, period_end, kind, freq, line_item));
-- the point-in-time view every agent tool reads through
CREATE VIEW vi.as_of AS SELECT * FROM vi.statements WHERE filed_at <= current_setting('vi.t0')::DATE;
04

The pipeline, stage by stage

Seven stages, each a CLI command with an idempotent output table, so any stage can be re-run without re-fetching upstream. Stage S3 runs inside transcript·lab.

S1 · catalog

Pull all ids, then metadata newest→oldest until createdAt < 2022-09-17. Uses transcript·lab's SupadataDiscoveryClient (imported as a path dependency, or simply its on-disk cache format) so the cache is shared.

uv run vi catalog --channel @Value-Investing --since 2022-09-17
→ vi.videos: 1,0xx rows · cache .vi/discovery_cache/

S2 · classify titles

One structured LLM call per title (+ description): kind, tickers[] with exchange, confidence. The 40 hand-labelled titles are the eval; target ≥ 95% agreement on kind before running the batch. Low-confidence rows go to a review list in the app.

S3 · ingest (in transcript·lab)

Only single and multi videos are fetched — roughly 750 transcripts instead of 2,072. Two ways to trigger it; both leave the corpus browsable in the workbench:

# a) one-shot from the transcript-rag-agent checkout
uv run python -m src.cli bulk-index channel --channel @Value-Investing \
   --since 2022-09-17 --label value-investing
# b) per-video, driven by vi so only classified videos are fetched
uv run vi ingest --kinds single,multi   # POST /api/index/queue per url
Option a) fetches macro videos too (≈250 wasted Supadata calls) but needs no new code. Option b) is the plan; a) is the fallback if the queue API is awkward to drive.

S4 · extract golden calls

Full raw transcript (from raw_transcripts, with timestamps) → one structured GoldenCall per ticker discussed. Cached by (video_id, transcript hash, extractor_version). See §5.

S5 · market data

For every distinct ticker: daily OHLCV back to 2018 (so the agent has 4 years of history at the earliest T0) and quarterly + annual statements. Benchmarks: SPY, plus a local index per exchange. Parquet cache under .vi/market/, then loaded into DuckDB. See §6.

S6 · agent + validate

vi run-agent --split test --prompt v1 writes one vi.predictions row per call; vi validate writes vi.validations for every call whose horizon has elapsed. Both are pure functions of DuckDB state, so a run is reproducible from the committed prompt version + the cached market data.

05

The golden set

The transcript sample confirms the channel states its conclusion explicitly ("if you don't want to watch the whole video … here is the conclusion", then a ranking and a 10–15-year view). That makes extraction tractable, but stance is not a clean buy/sell label: it is hedged, conditional and often relative ("might double, but will go bust in 10–15 years"). The schema has to capture that or the agent is being graded against noise.

# src/value_invest/golden/models.py
class GoldenCall(BaseModel):
    ticker: str; exchange: str | None
    stance: Literal["buy","hold","sell","watch","avoid"]
    stance_strength: Literal["strong","moderate","weak"]
    conditional_on: str | None      # "if it drops below $60"
    intrinsic_value: float | None   # his number, in quote ccy
    intrinsic_value_method: str | None
    price_mentioned: float | None   # sanity vs vi.prices at T0
    horizon_years: float | None
    thesis: list[str]               # 3–6 short claims
    risks: list[str]
    verifiable_claims: list[Claim]  # "P/E is 12" → fact-check
    evidence: list[Evidence]        # chunk ids + timestamps
    is_primary: bool                # main subject vs passing mention

How it is built and kept honest

  • Extractor: one long-context call per transcript with the schema above as a tool. Multi-stock videos emit several calls; passing mentions are kept but flagged is_primary=false and excluded from scoring by default.
  • Cross-check: price_mentioned vs actual close at T0 (±10 %) catches wrong ticker resolution and wrong dates for free.
  • Curation: same discipline as transcript·lab's docs/golden-set-curation.md — a hand-reviewed core (target 100 calls, stratified by stance and year) with curation_status=reviewed; the rest stay auto and are reported separately.
  • Inter-extractor agreement: run two extractor versions/models on the reviewed core and report κ on stance. If κ < 0.7 the stance taxonomy is wrong, not the models.
  • Fact-check: verifiable_claims ("dividend yield is 7 %") are checked against vi.as_of — a second, cheap accuracy signal about the channel itself.

Splits

By video date, not random: train ≤ 2024-06, test 2024-07 → 2025-06, holdout ≥ 2025-07 (sealed until the end). Time-based splits stop the prompt loop from learning 2025 market context and applying it to 2023 videos.

07

The analyst agent

Input is a ticker and a T0. The agent gets tools, not a data dump, so its trace shows what it looked at — which is what the app walks through and what the teacher in the improvement loop diagnoses.

tools
price_history(ticker, window) · statement(kind, freq, n) · ratios() (P/E, EV/EBITDA, FCF yield, net debt) · peer_snapshot() · prior_calls(ticker) (his own earlier calls on the same name, via transcript·lab RAG — opt-in, ablated)
guard
every tool reads through vi.as_of with t0 bound once per run; a test asserts no row with date > t0 can leak
output
AnalystReport: same fields as GoldenCall minus evidence, plus confidence and a markdown report
runtime
Pydantic AI agent through a single llm.py chokepoint (ConvFinQA pattern); DeepSeek for volume, Claude for the reviewed core; demo mode refuses model calls

How it "learns"

a · Prompt-optimisation loop first

DABStep/ConvFinQA loop: run train split → teacher reads first-wrong cases → proposes one prompt version → gate on test split (net-positive, McNemar-significant). Cheap, auditable, versioned in agents/vN/system.md.

b · Retrieval few-shot

Retrieve the k most similar earlier golden calls (by sector, stance, ratios) as worked examples. Strictly earlier than T0. Measured as an ablation of (a).

c · Fine-tune

900 examples is thin; only if (a)+(b) plateau, and then a small open model on the reviewed core. Explicit non-goal for the first milestone.

Baselines the agent must beat

  • majority stance — if 60 % of calls are "buy", a constant "buy" scores 60 %.
  • ratio rule — buy if FCF yield > 6 % and net debt/EBITDA < 2, else hold. Ten lines of SQL.
  • no-tools LLM — the same model given only ticker + date, to expose memorised knowledge of what happened later. Its score is the leakage floor; the tool agent must be scored on cases where this baseline is at chance.
Leakage is the real risk. A 2026 model knows Nike's 2024 story. The no-tools baseline and the date-based split are the two controls; the holdout ≥ 2025-07 is the only fully clean evidence, and it is small. Say so in the results rather than hide it.
08

Validation: were the calls right?

For every call and horizon h ∈ {6, 12, 24} months where T0 + h ≤ today:

ret        = adj_close(T0 + h) / adj_close(T0) − 1
bench_ret  = same for the ticker's benchmark index
excess     = ret − bench_ret
verdict    = correct     if (stance ∈ {buy}  and excess > +5 pp)
                         or (stance ∈ {sell,avoid} and excess < −5 pp)
                         or (stance ∈ {hold,watch} and |excess| ≤ 10 pp)
           = wrong       if the opposite sign beyond the same band
           = indeterminate otherwise

Thresholds are parameters in vi.validations' run config, not constants, so the app can show sensitivity. Prices are adjusted closes; a missing T0 + h trading day snaps to the next session.

Intrinsic-value check: for calls with an IV, did price reach it within the stated horizon (or 24 m)? Reported as a hit rate alongside stance verdicts.

11

Risks, then the decisions I need from you

high Model leakage of future knowledge

Controlled by the no-tools baseline, date splits and the sealed holdout; cannot be eliminated. Report it, don't hide it.

high Fundamentals depth for 2022–24 videos

yfinance alone leaves the agent blind for older US videos and all non-US ones. EDGAR fixes US; non-US stays shallow unless paid data is added.

med Stance is hedged, not binary

κ between extractors on the reviewed core decides whether the taxonomy holds. A 3-way collapse is the fallback headline metric.

med Supadata budget

≈1,050 metadata + ≈750 transcript calls. All cached; the catalog stage reports spend before ingest starts.

med Two stores drift

vi.videos is always rebuilt from transcript·lab's corpus API; a CI check compares counts.

low Ticker resolution errors

Caught by the price-mention cross-check and the review queue.
